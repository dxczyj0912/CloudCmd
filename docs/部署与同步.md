# 部署与同步

CloudCmd 仍可直接打开 `index.html` 离线使用；需要网页、手机浏览器和 Android App 共享进度时，运行仓库自带的 Node 服务。服务不需要 npm 依赖，静态文件、同步 API 和内容版本检查都由同一个进程提供。

## GitHub 推送后自动部署（无域名也可）

仓库的 `CloudCmd checks` 工作流在 `master` 分支的每次 push 后先运行数据、浏览器、手机布局和 APK 内容检查。检查全部通过，才把**该提交的源码**经 SSH 传到 `/opt/cloudcmd`，重建 Docker 容器并验证 `http://127.0.0.1:8787/api/health`。检查或健康检查失败会使工作流变红；已有版本会自动回退，第一次部署失败则需查看服务器日志。同步数据仍在 Docker 命名卷 `cloudcmd_cloudcmd-data` 中，不随代码目录替换。工作流传输的是已提交源码，未提交文件和被忽略的 APK 不会自动上传。

首次需要在服务器上安装 Docker Engine、Compose 插件和 `curl`，开放云安全组及主机防火墙的 TCP 8787，并准备一个能运行 `docker compose`、可写 `/opt/cloudcmd` 与 `/opt/cloudcmd-backups` 的 SSH 用户。以 `root` 登录时可直接运行：

```bash
mkdir -p /opt/cloudcmd /opt/cloudcmd-backups
docker compose version
curl --version
```

若使用普通 `deploy` 用户，则先由管理员建目录并执行 `sudo chown -R deploy:deploy /opt/cloudcmd /opt/cloudcmd-backups`，同时让该用户能运行 Docker。

若服务器已在 `/opt/cloudcmd` 运行旧版，请先备份该目录和 Docker 卷，再启用首次自动部署。部署脚本会保留旧目录的 `.env`、`apk/` 与根目录的 `CloudCmd-*.apk`；其余本地手改内容应先提交到仓库。旧文件会移到 `/opt/cloudcmd-backups/时间-提交摘要/previous`，健康检查失败时会恢复它。长期运行后可按需清理已经不再需要的旧备份。

先核对服务器 SSH 主机公钥指纹，再把对应的 `known_hosts` 行填入 GitHub Secret；不能只靠未核对的 `ssh-keyscan` 结果建立信任。登录可二选一：推荐为 GitHub Actions 创建**专用部署 SSH 密钥**，把公钥加入服务器用户的 `~/.ssh/authorized_keys`；如果服务器暂时不能添加公钥、但允许密码登录，则由你自己在 GitHub Secret 配置 `DEPLOY_PASSWORD`。不要在聊天或仓库中发送服务器密码。到 GitHub 仓库的 **Settings → Secrets and variables → Actions → New repository secret** 配置：

| Secret | 内容 |
| --- | --- |
| `DEPLOY_HOST` | 服务器公网 IP，不含 `http://` |
| `DEPLOY_USER` | 有上述权限的 SSH 用户名 |
| `DEPLOY_SSH_PORT` | SSH 端口；不填按 22 |
| `DEPLOY_SSH_KEY` | 选用密钥登录时填专用部署私钥的完整文本；与 `DEPLOY_PASSWORD` 二选一 |
| `DEPLOY_PASSWORD` | 选用密码登录时填 SSH 用户密码；与 `DEPLOY_SSH_KEY` 二选一，工作流不会把密码写入命令参数或日志 |
| `DEPLOY_KNOWN_HOSTS` | 核对指纹后的 SSH 主机公钥行；非 22 端口应使用 `[IP]:端口` 格式 |

当前这台服务器的控制台指纹已与网络获取值核对为 `SHA256:4nvvLIJHbWBCjhYWEbs73ktn7DuI5jqts6y9ZvBf/+M`。本机核对过的完整 `known_hosts` 行保存在 `C:\Users\23881\CloudCmd-keys\server-known-hosts`；用 PowerShell 执行 `Get-Content 'C:\Users\23881\CloudCmd-keys\server-known-hosts' -Raw | Set-Clipboard`，直接粘贴到 `DEPLOY_KNOWN_HOSTS`。本项目使用 `DEPLOY_HOST=1.117.66.63`、`DEPLOY_USER=root`、`DEPLOY_SSH_PORT=22`。密码方案让 GitHub Actions 获得服务器登录权限；条件允许时可改成仅有部署权限的专用用户和密钥。

这几个 Secret 配好后，在本机设置 GitHub 远端并推送**审核过的项目文件**，例如：

```bash
git remote add origin https://github.com/你的用户名/你的仓库.git
git status --short
git add .github .dockerignore .gitignore Dockerfile docker-compose.yml server.js tools assets data android index.html academy-lab.html README.md docs
git diff --cached --stat
git commit -m "Add automatic server deployment"
git push -u origin master
```

已有 `origin` 时用 `git remote set-url origin ...`；提交前务必核对暂存区。`apk/`、`backup/`、根目录 APK、`.env` 和签名文件都被 Git 忽略。推送后在 GitHub **Actions → CloudCmd checks** 查看 `verify` 与 `deploy`；部署通过后用 `http://服务器IP:8787/api/health` 和主页验收。之后网页代码更新只需提交并推送 `master`，检查通过后服务器会自动更新，打开中的网页约 30 秒内提示刷新。缺少登录 Secret 时，仓库内的自动化文件已就绪，但部署步骤无法连接服务器。

### 单独发布手机 APK

发新版时，先把两个网页的品牌版本、Android `app_name` 和页内品牌文字一起更新并推送；构建脚本会拒绝与页面显示不一致的正式版本号。签名构建完成后，本地旧安装包自动移入 `backup/`，服务器旧包仍保留在服务器部署备份中。

网页推送不会自动改变 APK 版本号。需要 Android 离线资源更新时，打开 GitHub **Actions → Publish signed Android APK → Run workflow**，选择 `master`，输入新的 `version_name`（从 `0.0.1` 开始）与**比当前发布版更大的** `version_code`（`0.0.1` 为 9）。先不勾选 `publish` 可只构建、验签并下载构建产物；确认后勾选 `publish` 再运行，才会发布到服务器。工作流用原有证书签名、做完整检查、核对证书 SHA-256 指纹，再把 APK 放到服务器的 `apk/` 目录。`/api/app-version` 随即返回新版本和下载地址；手机端检查到新版本后可下载并安装。无需重建同步服务容器，因为 `apk/` 是只读挂载目录。

在同一 GitHub Secrets 页面额外配置：

| Secret | 内容 |
| --- | --- |
| `APK_KEYSTORE_BASE64` | **现有** `.p12` 证书文件的 Base64 内容，不要新建证书 |
| `APK_KEY_ALIAS` | 现有证书的 key alias |
| `APK_KEYSTORE_PASS` | 现有证书库密码 |
| `APK_KEY_PASS` | 现有私钥密码，若相同仍单独填写 |
| `APK_CERT_SHA256` | 已安装 APK 的签名证书 SHA-256 指纹，用来阻止错误证书发布 |

Windows PowerShell 可用 `[Convert]::ToBase64String([IO.File]::ReadAllBytes('证书文件绝对路径')) | Set-Clipboard` 复制证书 Base64，直接粘贴到 Secret；不要把它写入仓库或聊天记录。签名指纹可从**当前能覆盖安装的旧 APK**用 Android SDK 的 `apksigner verify --print-certs` 读取。当前已发布版本的 `versionCode` 可看 `http://服务器IP:8787/api/app-version`；首次使用这套发布流程时，需确保输入值大于已安装 APK 的 versionCode。GitHub Actions 的构建产物保留 30 天，服务器会继续保存正式 APK。

## 本机或服务器启动

```bash
node server.js
```

默认监听 `0.0.0.0:8787`。浏览器访问 `http://服务器地址:8787/`，手机访问同一个 HTTPS 域名即可。生产环境应在 Nginx、Caddy 或云负载均衡后启用 HTTPS，并把同步服务的 `CLOUDCMD_CORS_ORIGIN` 限定为实际站点来源。

也可以使用 Docker：

```bash
docker compose up -d --build
```

同步数据保存在容器卷 `/data/sync-sessions.json`，升级站点镜像不会丢失。备份该卷前先停止写入或复制文件，避免半写入状态。

## 配对设备

1. 在第一台设备打开“进度备份与同步”，填写部署地址，点击“新建同步码”。
2. 在手机或另一台电脑打开同一地址，填写相同部署地址和同步码，点击“连接同步”。
3. 两台设备会合并已掌握命令、收藏、课程步骤、复习记录和主题设置；后续变更通过 SSE 实时通知，断线时每 60 秒补偿同步。

同步码是访问该进度的 bearer secret。不要把同步码写进截图、工单或公开链接；丢失同步码只能重新创建会话。服务端不执行任何命令，也不保存命令终端内容，只保存进度 JSON。

## 内容实时更新

部署版每 30 秒检查 `/api/version`。当 `data/` 或 `assets/` 发生新版本时，页面顶部出现刷新提示；刷新后加载最新课程、卡片和命令数据，不会强制打断正在输入的终端。

Android APK 默认仍保留离线资源。给 APK 配置同步服务后可以同步进度、检查内容版本并获得 APK 更新提示；若要直接使用服务器最新内容，也可以用手机浏览器打开部署地址。这样保留了离线回退能力，也不会在未知服务器上静默替换学习内容。

## APK 更新提示

把正式签名的 APK 放在部署目录根部，例如 `CloudCmd-0.0.1.apk`，服务会通过 `/api/app-version` 返回最新版本和完整 HTTP(S) 下载地址。也可以不把 APK 放进镜像，改用环境变量指向对象存储或 CDN：

```bash
CLOUDCMD_APK_URL=https://download.example.com/CloudCmd-0.0.1.apk
CLOUDCMD_APP_VERSION=0.0.1
CLOUDCMD_APP_VERSION_CODE=9
```

Android App 会把自身 `versionName` 和 `versionCode` 发给网页。新版按递增的 `versionCode` 判断更新；升级到 `0.0.1` 期间，服务器给只认识旧显示版本号的 1.x 客户端返回兼容提示。页面显示“下载更新”后由系统浏览器下载 APK，再由 Android 系统确认安装。更新包必须使用与已安装版本相同的签名密钥，否则不能覆盖安装；`--no-sign` 调试 APK 不能作为正式更新包。旧版客户端的过渡提示会暂时显示 `1.3.5`，实际下载并安装的是 `0.0.1`。

若旧版点击下载出现 `file:///CloudCmd-版本.apk`，说明服务器仍返回相对路径。上传新 `server.js` 并重新构建容器；`curl http://服务器IP:8787/api/app-version` 的 `apkUrl` 应以 `http://` 或 `https://` 开头。新版 App 也会将相对路径按同步服务地址解析。

## 环境变量

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `PORT` | `8787` | HTTP 监听端口 |
| `HOST` | `0.0.0.0` | 监听地址 |
| `CLOUDCMD_DATA_DIR` | `./server-data` | 同步会话持久化目录 |
| `CLOUDCMD_CORS_ORIGIN` | `*` | API 的跨域来源；生产环境应收紧 |
| `CLOUDCMD_APK_FILE` | 自动寻找 `CloudCmd-*.apk` | 部署目录内的 APK 文件名 |
| `CLOUDCMD_APK_URL` | 空 | 外部 APK 下载地址；设置后优先于本地文件 |
| `CLOUDCMD_APP_VERSION` | 从 APK 文件名推断 | APK `versionName` |
| `CLOUDCMD_APP_VERSION_CODE` | `0` | APK `versionCode`，用于发布台账 |

同步 API 只接受有限大小的 JSON，服务端对进度字段做合并，不接受路径、命令执行或任意文件写入。真实部署仍需配合 HTTPS、访问日志、磁盘备份和反向代理限流。

无域名使用 HTTP 公网 IP 时，Android APK 必须使用允许明文 HTTP 的版本（当前 `CloudCmd-0.0.1.apk`）。手机浏览器先访问 `http://服务器IP:8787/api/health`：如果打不开，检查云安全组 TCP 8787、Rocky Linux 的 `firewalld` 和 Compose 端口映射；如果浏览器能打开但 App 不能连接，安装最新签名 APK，并确认地址不是 `127.0.0.1` 或 `localhost`。
