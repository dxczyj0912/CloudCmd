# 03 · 独立云主机部署

目标：在一台**新建的测试云主机**上部署同一个 CloudCmd 项目，并从本机通过 SSH 隧道访问。不要在承载现有网页、同步数据或其他业务的服务器上做本实验。本篇的云主机命令以 **Ubuntu 24.04 LTS 的 Bash** 为例；其他发行版需按对应官方文档调整。

## 准备测试机

1. 在云控制台新建一台测试机。建议 2 vCPU、4 GB 内存、20 GB 系统盘起步，记录区域、实例 ID、系统版本和公网 IP。按小时计费时先设预算提醒。
2. 安全组只允许**你的公网 IP**连接 TCP 22。**不要开放 18788**；服务仅绑定云主机的 `127.0.0.1`。
3. 在本机 PowerShell 登录，`<测试机公网IP>` 要替换成实际地址；首次连接先通过云控制台核对 SSH 主机指纹：

```powershell
ssh ubuntu@<测试机公网IP>
```

如果实例默认用户名不同，请用镜像文档给出的用户。不要把云密码、私钥或个人同步码写进实验记录。

## 在云主机 Bash 中部署

安装运行本实验所需的软件，确认 Docker Compose 可用：

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-v2 git curl
sudo systemctl enable --now docker
sudo docker compose version
```

若发行版的软件源没有 `docker-compose-v2`，按 [Docker 官方 Ubuntu 安装指南](https://docs.docker.com/engine/install/ubuntu/)安装 Compose 插件，然后继续。以下仓库地址是本项目地址；**需要先把这套实验文档和配置提交、推送到仓库**，云主机 clone 后才会有 `docs/真实项目实战/files/compose.lab.yml`。私有仓库要事先配置**只读**访问凭据，不能把个人 token 放进 clone URL：

```bash
git clone https://github.com/dxczyj0912/CloudCmd.git cloudcmd-lab
cd cloudcmd-lab
sudo docker compose -p cloudcmd-lab -f docs/真实项目实战/files/compose.lab.yml config
sudo docker compose -p cloudcmd-lab -f docs/真实项目实战/files/compose.lab.yml up -d --build
sudo docker compose -p cloudcmd-lab -f docs/真实项目实战/files/compose.lab.yml ps
curl -fsS http://127.0.0.1:18788/api/health
```

健康接口应返回 `"ok":true`。`sudo ss -lntp | grep 18788` 应看到服务只在本机回环地址监听。若 `apt` 报锁、软件包不可用或 Docker 权限错误，先解决环境问题，不要跳过 `config` 与健康检查。

## 从本机访问

保持云主机上的服务运行。在**本机新的 PowerShell 窗口**建立 SSH 隧道：

```powershell
ssh -N -L 18789:127.0.0.1:18788 ubuntu@<测试机公网IP>
```

这个窗口保持打开。再开一个本机 PowerShell 窗口：

```powershell
Invoke-RestMethod http://127.0.0.1:18789/api/health
```

浏览器访问 `http://127.0.0.1:18789/`，应显示云主机提供的 CloudCmd 页面。隧道里的 `127.0.0.1` 指向云主机的回环地址；公网安全组无需开放应用端口。

## 验收与收尾

记录云主机系统版本、Docker 版本、容器状态、云主机本地健康结果、本机隧道访问结果与安全组规则。随后在本机按 `Ctrl+C` 关闭隧道。在云主机上执行下面的命令停止**测试**容器：

```bash
sudo docker compose -p cloudcmd-lab -f docs/真实项目实战/files/compose.lab.yml down
```

测试完成后在云控制台释放测试实例及其附属计费资源；释放前核对实例 ID，并保存需要的脱敏证据。下一关的备份恢复在本机 Docker 做，不依赖这台云主机。
