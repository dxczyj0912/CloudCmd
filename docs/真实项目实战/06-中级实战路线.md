# 中级云运维 / DevOps 实战路线

先按[初级云计算 J0–J9 项目](README.md)掌握单服务运行、云资源、网络、存储、监控、备份和 Kubernetes 基本发布。**它们是入门基础，不是“做完即中级”。**中级训练必须在没有固定答案的真实故障里，把服务、数据库、网络、发布、数据、自动化和监控串起来。

下面选六个有公开源码或官方教程的项目。按顺序完成，不要求一次装齐。每个项目使用独立实验环境；不要把现有 CloudCmd 同步服务器当实验机。

| 顺序 | 项目与原始资料 | 核心任务 | 建议环境 |
| --- | --- | --- | --- |
| M1 | [Gitea + PostgreSQL](https://github.com/docker/awesome-compose/tree/master/gitea-postgres)、[Gitea Docker 文档](https://docs.gitea.com/installation/install-with-docker) | 双服务部署、网络、数据库和 Git 数据的备份恢复、升级回滚 | 本机 Docker 或独立测试云主机；公网部署前补 HTTPS 与访问控制 |
| M2 | [Terraform Docker 教程](https://developer.hashicorp.com/terraform/tutorials/docker-get-started)与[腾讯云 Provider](https://registry.terraform.io/providers/tencentcloudstack/tencentcloud/latest/docs) | plan 审核、云资源漂移、可控销毁 | 本机 Docker + 独立云测试项目 |
| M3 | [Online Boutique](https://github.com/GoogleCloudPlatform/microservices-demo)、[本地集群开发指南](https://github.com/GoogleCloudPlatform/microservices-demo/blob/main/docs/development-guide.md) | 多服务 K8s 部署、滚动发布、资源与依赖排障 | 资源充足的本机集群；官方本地指南给 Minikube 至少 4 CPU、4 GiB、32 GB 磁盘，Docker Desktop 至少 3 CPU、6 GiB |
| M4 | [Argo CD Example Apps](https://github.com/argoproj/argocd-example-apps)、[官方入门](https://argo-cd.readthedocs.io/en/stable/getting_started/) | 先用 Guestbook 入门，再用 GitOps 管理 M3 的 Online Boutique | 另建资源充足的本地实验集群 |
| M5 | [OpenTelemetry Demo](https://github.com/open-telemetry/opentelemetry-demo)、[Docker 部署指南](https://opentelemetry.io/docs/demo/docker_deployment/) | 用指标、日志、链路追踪定位跨服务问题并写事故复盘 | 独立、资源充足的本机或测试环境 |
| M6 | [腾讯云 CLB](https://cloud.tencent.com/document/product/214) 与两台测试机 | 健康探测、流量切换、故障恢复和有状态边界 | 独立云测试 VPC；短时运行并控制费用 |

## M1 · 交付一个可恢复的双服务应用

1. 按官方 Gitea Docker 文档在**仅本机可访问**的实验环境部署 Gitea 和 PostgreSQL。官方 Awesome Compose 样例可作为结构参考，但其 `latest` 镜像和演示密码只适合看结构；实际实验要记录明确版本，并把密码留在仓库外。
2. 创建一个测试仓库，提交一个文件，完成一次 clone → 修改 → push。记录 Gitea 页面、数据库、网络和两个数据卷的关系，能画出请求到数据落盘的路径。
3. 分别停止 Gitea 和数据库容器，观察网页、容器日志与数据库日志的差异。先提出“应用挂了、数据库挂了、连接断了”三个假设，再用证据排除错误假设。
4. 按 [Gitea 官方备份与恢复文档](https://docs.gitea.com/administration/backup-and-restore)备份**仓库文件和数据库**，在新的项目名与新卷中恢复。用原测试仓库的提交哈希、页面数据和 Git clone 验证，不能只以“容器启动”为通过。
5. 在可恢复前提下做一次版本升级；记录升级前镜像摘要、数据库备份、兼容性说明与回滚路径。升级失败时回到旧版本，并再次验证测试仓库。不要通过覆盖旧卷来“恢复”。

**M1 通过**：你能在 30 分钟内从空卷恢复测试仓库，并用命令、日志说明一次故障是应用层还是数据库层。没有恢复演练证据，M1 不算完成。

## M2 · 把基础设施变成可审查的代码

按[Terraform 项目逐步操作](07-Terraform基础设施即代码.md)先管理本地 Docker，再在独立云测试项目里管理一个新资源。核心不是执行 `apply`，而是能预判 plan、解释真实资源与 state 的差异，并在 destroy 前认出所有将被删除的目标。

**M2 通过**：提交脱敏的代码与 plan、一次漂移检测、一次人工审核记录、资源创建和清理证据。没有可重建的代码或销毁核验，不算完成。

## M3 · 运维一个多服务 K8s 应用

1. 按 Online Boutique 的[本地集群开发指南](https://github.com/GoogleCloudPlatform/microservices-demo/blob/main/docs/development-guide.md)创建隔离集群，记录仓库提交、集群版本、节点资源。先确认资源充足，再运行指南中的 `skaffold run`。首次构建可能较慢。
2. 查看所有 Pod、Deployment、Service 和 Events；画出浏览器请求经过 frontend，再到商品、购物车、支付等服务的路径。通过官方提供的端口转发访问页面，并完成一次浏览、加入购物车和结账流程。
3. 发布一个故意不存在的 frontend 镜像标签。比较 `kubectl rollout status`、新旧 Pod、`describe` Events 和用户访问结果；解释为什么“网页还可打开”不能证明新版本发布成功。回滚后验证镜像和业务流程。
4. 在**自己的实验集群**分别模拟一项依赖不可达和一项资源不足。每次先写假设，再查 Service/Endpoints、Pod 日志、Events、资源请求与限制；恢复后重新验证业务流程。
5. 写一份发布运行手册：变更前检查、部署命令、成功判据、失败停止条件、回滚命令和清理命令。另写一份故障复盘，注明时间线、影响范围、根因、证据和预防措施。

**M3 通过**：面对未提前告诉根因的 Pod 起不来、服务不可达或发布失败，能在 45 分钟内定位层次、恢复服务，并拿出发布前后证据。只跑通 `skaffold run` 不算完成。

## M4 · 用 Git 管住发布状态

按[Argo CD GitOps 项目逐步操作](08-ArgoCD-GitOps发布.md)先用 Guestbook 熟悉控制器，再在独立集群由 Git 发布 M3 的 Online Boutique；经历 Git 变更、集群手工漂移、错误提交和 Git 回退。把“Git 期望状态”与“集群实际状态”逐次对比。

**M4 通过**：交付提交链、同步与漂移证据、失败发布和恢复后的用户流程验证；只会在页面点 Sync 不算完成。

## M5 · 用可观测性证明根因

1. 按 [OpenTelemetry Demo Docker 指南](https://opentelemetry.io/docs/demo/docker_deployment/)在独立环境运行演示应用。记录该版本实际启动的服务、入口地址和资源消耗，先能完成正常用户流程。
2. 从一个用户请求开始，找到相应 trace；指出慢在哪个服务、哪段 span，关联该服务的指标和日志。记录请求时间、trace ID、异常或高延迟判据。
3. 使用演示项目提供的故障场景，或者只在实验环境制造一个服务不可达问题。先从用户现象和告警入手，不直接看“答案”；按指标 → trace → 日志 → Pod/容器状态逐层缩小范围。
4. 设一个可检查的服务目标，例如“测试请求成功率”和“P95 延迟”，说明统计窗口、数据来源与误报边界。修复后用同一查询口径对比，不只看某一张截图。
5. 提交一份事故报告：发现时间、影响、证据链、根因、恢复操作、验证与后续改进。让其他人仅凭报告能重复定位。

**M5 通过**：能用同一个请求的 trace、指标和日志互相印证，而不是看到 Grafana 看板就打勾。

## M6 · 证明入口流量能在实例故障时切换

按[双机负载均衡与故障切换项目](09-双机负载均衡与故障切换.md)部署两个可区分的无状态后端。分别制造进程停止和网络规则阻断，记录 CLB 健康检查、请求错误数、切换和恢复时间。

**M6 通过**：能用用户请求与健康检查结果证明故障收敛，且明确说明本实验**没有验证有状态数据高可用**；只看到两个健康后端不算完成。

## 最终通关标准

六关都要**不照抄答案独立重做一次**。请另一人随机指定至少六种故障或变更：应用不可用、数据库或依赖不可用、K8s 发布失败、IaC 漂移、性能变慢、CLB 后端失效。每次必须交出以下证据：

1. 故障前的正常基线与受影响用户动作。
2. 至少两个候选根因及其排除证据。
3. 修复或回滚记录、数据一致性检查、恢复后的业务验证。
4. 事故时间线和运行手册改进。

建议把项目放进一个独立的实战仓库，提交**脱敏的** Compose/K8s 配置、架构图、运行手册和事故报告；备份文件、同步码、密码和私钥留在仓库外。真实环境证据可按 [CloudCmd 验收模板](../真实环境验收模板.json)记录。

达到上述标准，才可以说“具备中级云运维 / DevOps 的**项目实操基础**”，而不是仅仅完成课程。是否能独立承担生产环境的中级岗位，还要经过真实变更、值班、协作和长期运行检验。高级能力另需架构设计、容量与成本取舍、多区域容灾和长期可靠性负责；不在这条路线的通过声明内。

需要转向存储或私有云岗位时，再做 [Ceph 三节点存储与故障恢复](10-Ceph三节点存储实战.md)和 [OpenStack DevStack 私有云](11-OpenStack私有云实战.md)。它们是资源要求更高的专修项目，不应与六关中级核心任务机械叠加，也不在现有 4 GB CloudCmd 服务器上执行。

## 资料与验证边界

上述仓库和官方文档链接在 2026-09-28 核对过可访问。版本、命令和资源要求以动手当天的官方文档为准。当前仓库只实测了 CloudCmd 本机运行项目与 Docker Compose 配置解析；M1–M6 操作尚未在此工作区真机跑通，不能标记为已验收。
