# 09 · 双机负载均衡与故障切换

这是中级路线的云平台项目。前置：[云网络与安全组](03A-云网络与安全组.md)、[云监控与告警](04A-云监控与告警.md)。在同一个测试 VPC 内短时创建两台测试机和一个测试 [腾讯云 CLB](https://cloud.tencent.com/document/product/214)，不用正在运行的 CloudCmd 同步服务器。CLB 与两台实例都可能计费；先核对区域、带宽和清理计划。

本项目只验证**无状态 HTTP 服务**的流量切换。CloudCmd 同步数据目前保存在本机数据卷，直接在两台机器各运行一份不会自动成为数据高可用；不能把本实验的结果套用到同步服务。

## 逐步操作

1. 在测试 VPC 内创建两台小规格测试机 A、B，条件允许时放在不同可用区。记录两台实例 ID、私网 IP、可用区和安全组。先从管理机分别通过 SSH 登录，确认系统时间、网络和剩余磁盘空间正常。
2. 在 A、B 各建一个只含 `index.html` 的测试目录，A 页面写 `backend-A`，B 页面写 `backend-B`。两台都用 `python3 -m http.server 18792 --bind 0.0.0.0 --directory <测试目录>` 临时运行。每台本机先执行 `curl -i http://127.0.0.1:18792/`，再从另一台通过私网 IP 验证，确认应用监听与私网规则正确。
3. 创建测试 CLB、HTTP 监听和后端目标组，转发到 A、B 的 TCP 18792。健康检查路径用 `/`，成功码按该版本 CLB 文档设置；记录监听器、目标组、探测间隔与超时。安全组只开放测试所需的公网入口和 CLB 到后端的路径，不向全网开放后端 18792。
4. 从本机请求 CLB 公网 IP 十次以上，记录响应中的 `backend-A` / `backend-B`，再查看 CLB 控制台的两个后端健康状态。看到交替或不同后端响应只是分流证据；两个后端都被判健康才是基线。
5. 在 A 上停止临时 HTTP 服务，记录停止时间。继续定时请求 CLB，观察 A 被判不健康的时间与期间请求错误数。健康检查收敛后，响应应全部来自 B。重启 A 的服务，记录恢复健康与重新参与分流的时间。
6. 故意把 B 的测试安全组规则收紧到阻断 CLB 健康检查，比较“进程正常但 CLB 判不健康”的证据。恢复规则后再次确认双后端健康。复盘时分别解释应用、主机防火墙、安全组和 CLB 健康检查各自能造成什么现象。

## 验收与收尾

### 逐步命令与检查点

控制台创建两个**新测试实例**与 CLB，记下 A/B 实例 ID、私网 IP、CLB ID、监听器及目标组 ID；下列 Bash 只在实验机执行。任何 ID 与台账不一致就停下，不改现有 CloudCmd 服务。

1. **两台后端各自启动并本机验证：**在 A 执行 `mkdir -p "$HOME/clb-lab" && printf 'backend-A\n' > "$HOME/clb-lab/index.html"`，在 B 将 `A` 改成 `B`。各自执行 `python3 -m http.server 18792 --bind 0.0.0.0 --directory "$HOME/clb-lab"` 并保持运行；另开终端执行 `ss -lntp | grep ':18792 '` 与 `curl -fsS http://127.0.0.1:18792/`。**检查：**A/B 分别返回自己的标识；本机不通，先修服务，不创建 CLB。
2. **私网互访：**在 A 执行 `curl -fsS --max-time 5 http://<B私网IP>:18792/`，B 对 A 做同样请求。**检查：**返回对端标识；若失败先核对私网 IP、系统防火墙及安全组，只开放实验来源。
3. **配置 CLB 并验证健康：**在控制台创建测试 HTTP 监听、目标组和 `/` 健康检查，两个后端端口均为 18792。**检查：**控制台两个后端均显示健康，记录探测间隔、阈值与目标 ID；只有一个健康就停下排障。
4. **从用户入口取样：**在本机 PowerShell 执行：

   ```powershell
   $clbIp = '<实验CLB公网IP>'
   1..20 | ForEach-Object { "$(Get-Date -Format o) $((Invoke-WebRequest "http://$clbIp/").Content.Trim())"; Start-Sleep -Seconds 1 }
   ```

   **检查：**样本中能看到两个标识，且无非预期错误；有会话保持时可能集中到一台，须结合目标组转发统计判断，不把 20 次相同结果直接当故障。
5. **故障与恢复：**停止 A 的临时 HTTP 进程，继续运行第 4 步的采样，记录错误请求数与 CLB 判 A 不健康的时间；恢复 A 进程后继续采样，直到控制台双后端健康。**检查：**收敛后只由 B 响应，恢复后 A 重新参与。再只在 B 的实验安全组阻断 CLB 探测，复测并恢复规则。记录“进程停了”和“进程在但安全组挡住”两条不同证据链。

先删除测试 CLB 监听和实例绑定，再释放 CLB、公网地址与两台测试机，核对关联磁盘和监控策略是否仍在计费。文档及实验结果不能被表述为有状态应用的高可用架构；下一阶段需要独立设计共享数据、复制、备份和 RPO/RTO。
